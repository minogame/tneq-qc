
# Contraction Strategy Module Documentation

> Strategy / Contractor — Compilation and execution of tensor network contraction paths

---

## 1. Overview

Tensor network contraction is the process of progressively contracting multiple local tensors into a scalar or low-rank tensor via Einstein summation. Different contraction orderings can lead to drastically different computational complexity and memory usage.

tneq-qc adopts a **Strategy Pattern** design:

```
ContractionStrategy (ABC)
├── EinsumStrategy        # opt_einsum global optimization
├── GreedyStrategy        # Greedy step-by-step contraction
└── RowPriorityStrategy   # Row-by-row qubit contraction

StrategyCompiler          # Automatic optimal strategy selection
```

Users do not need to invoke strategies directly. `EngineCommon` internally handles strategy selection and compilation via `StrategyCompiler`.

---

## 2. Strategy Comparison

| Dimension | EinsumStrategy | GreedyStrategy | RowPriorityStrategy |
|---|---|---|---|
| **Principle** | Uses the `opt_einsum` library to globally optimize Einstein summation paths | Greedily selects the tensor pair with the lowest contraction cost at each step | Contracts row by row from top to bottom by qubit, controlling intermediate state size |
| **Time Complexity** | Compilation $O(n!)$ but optimized in practice by opt_einsum | $O(n^2)$ selection per step | Linear in the number of qubits |
| **Memory** | Generates the full expression at once; intermediate states can be large | Controllable, but depends on greedy choices | Strictly controlled: each step retains at most $O(\chi^2)$ sized intermediate tensors |
| **Use Cases** | qubit ≤ 20, few cores | Medium scale | Many qubits (100+), sparse connectivity (MPS/tree) |
| **Graph Logic Source** | `qctn.get_einsum_info()` | `qctn.adjacency_table` | `qctn.build_graph()` |

## 3. Detailed Strategy Descriptions

### 3.1 EinsumStrategy

**Location**: `tneq_qc/contractor/einsum_strategy.py`

Represents the entire tensor network as a single Einstein summation expression and delegates path optimization to `opt_einsum`:

```python
# Internal flow
einsum_eq, shapes = qctn.get_einsum_info(cs_shapes, mx_shapes)
# einsum_eq is of the form: "abc,bcd,cde->ae"
expression = oe.contract_expression(einsum_eq, *shapes)
result = backend.execute_expression(expression, *tensors)
```

Advantages:
- Extremely fast execution after compilation
- opt_einsum automatically finds a near-optimal contraction path
- Supports transparent switching between PyTorch / JAX backends

Disadvantages:
- Long compilation time when there are many cores
- Intermediate tensors may exceed memory

### 3.2 GreedyStrategy

**Location**: `tneq_qc/contractor/greedy_strategy.py`

At each step, selects the pair of tensors with the lowest contraction cost to merge, until only one tensor remains:

```
Step 1: Select lowest-cost pair (A, B) → AB
Step 2: Select lowest-cost pair (AB, C) → ABC
Step 3: ...
```

### 3.3 RowPriorityStrategy

**Location**: `tneq_qc/contractor/row_priority_strategy.py`

Designed specifically for large-scale MPS / BornMachine models. Contracts row by row from top to bottom by qubit:

```
Qubit 0: Contract all cores in this row → intermediate tensor T₀
Qubit 1: Contract T₀ with qubit 1 cores → T₁
...
Qubit N: Contract T_{N-1} → scalar result
```

For BornMachine structures, each qubit row contains 5 tensors (CS, TN, Mx, TN_h, CS_t), and uses a symmetric unfolding graph within each row:

```
Symmetric unfolding structure generated by build_graph():

qubit i:
  CS_i ─── TN_i ─── Mx_i ─── TN_h_i ─── CS_t_i
   │         │                  │           │
   ↓         ↓                  ↓           ↓
  (bond     (bond              (bond       (bond
   to next)  to next)           to next)    to next)
```

Three-step internal flow of `build_graph()`:
1. **Embed**: Embed cores from the adjacency_table into left/right/Mx positions
2. **Wire**: Establish bond connections between cores of adjacent rows
3. **Symbolize**: Assign einsum symbols to all connecting edges

## 4. StrategyCompiler

**Location**: `tneq_qc/contractor/compiler.py`

Selects a strategy by registered name. Passing a list keeps the cost-based
selection behavior among those named candidates.

```python
compiler = StrategyCompiler(strategy='row_priority')

compute_fn, strategy_name, cost = compiler.compile(qctn, shapes_info, backend)
result = compute_fn(cores_dict, None, None)
```

Compilation flow:
1. For each candidate strategy, call `check_compatibility(qctn, shapes_info)` to check applicability
2. For compatible strategies, call `estimate_cost(qctn, shapes_info)` to estimate FLOPs
3. Select the strategy with the lowest cost
4. Call `get_compute_function(qctn, shapes_info, backend)` to generate an executable function

## 5. Custom Strategies

Implement the `ContractionStrategy` interface to register a new strategy:

```python
from tneq_qc import ContractionStrategy, register_contraction_strategy

class MyStrategy(ContractionStrategy):
    @property
    def name(self) -> str:
        return "my_strategy"

    def check_compatibility(self, qctn, shapes_info) -> bool:
        # Check whether the network structure is suitable for this strategy
        return True

    def estimate_cost(self, qctn, shapes_info) -> float:
        # Return estimated FLOPs
        return 1.0

    def get_compute_function(self, qctn, shapes_info, backend):
        # Return compute_fn(cores_dict, state_inputs, measures) -> result
        def compute(cores_dict, state_inputs, measures):
            ...
            return result
        return compute

# Register by strategy name. No mode registration is required.
register_contraction_strategy(MyStrategy())

engine = EngineCommon(backend=backend, strategy="my_strategy")
```

You can also inspect the current registry:

```python
from tneq_qc import get_registered_contraction_strategies

print(get_registered_contraction_strategies().keys())
```

## 6. Usage Recommendations

| Scenario | Recommended strategy | Reason |
|---|---|---|
| Quick prototyping (qubit < 15) | `'einsum_default'` | EinsumStrategy compiles fast and executes fast |
| Regular training (qubit 15-100) | `'row_priority'` | Directly uses RowPriority and avoids einsum selection |
| Large-scale training (qubit 100+) | `'row_priority'` | Stable large-scale contraction |
| BornMachine / batched Mx training | `'row_priority'` | Avoids selecting einsum on embedded batched measurement cores |

Users normally specify a strategy name when creating `EngineCommon`:

```python
engine = EngineCommon(backend=backend, strategy='row_priority')
result = engine.contract(qctn)  # Internally auto-compiles and caches the strategy
```

Strategy compilation results are cached on the QCTN instance, so subsequent `contract` calls on the same instance reuse the cached result directly.
